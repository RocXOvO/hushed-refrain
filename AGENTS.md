# Project memory for AI agents

This file is the durable architecture map for `ncm-comment-finder`. Read it before changing code. Keep it factual and compact; it describes the current system, not a changelog.

## Product and runtime shapes

The app finds public comments authored by a target user on NetEase Cloud Music or QQ Music. NetEase matches a numeric UID; QQ resolves a numeric QQ, profile URL, or EncryptUin to a canonical EncryptUin and compares the full opaque value. It has three runtime shapes over the same TypeScript core:

QQ scanning still treats canonical EncryptUin as opaque identity. Its production target parser accepts established opaque values without requiring reversibility. The separate single-input experiment in `src/qq-music/classic-encrypt-uin.ts` accepts only a supported EncryptUin, one exact allowlisted `https://y.qq.com` profile URL, or a 5..12/19-digit candidate; it must never change scan target keys, generations, checkpoints, reports, or author matching. Classic 8/12/16-character tokens decode only to a `qq-number-candidate`; strict 28-character tokens decode only to a 19-digit `wxuin-candidate`, displayed as `QQ音乐微信内部ID（wxuin候选）`, never a WeChat number. Bare/URL tokens stay local; numeric candidates require an explicit lookup. Network lookup is fail-closed when a pool or explicit proxy is selected; direct access is allowed only by explicit `allowDirect`, with no silent fallback. Keep full URLs, tokens and decoded identifiers out of logs, errors, screenshots, fixtures and Release notes; tests use synthetic identifiers. The API response and renderer memory hold `identifier`, but visible DOM and clipboard output stay masked until explicit reveal/copy.

- CLI: NetEase uses `src/cli.ts` via `npm run start -- <command>`; QQ uses the independent `src/qq-cli.ts` source entry.
- Local web dashboard: `src/server.ts` serves `web/` on `127.0.0.1`; run with `npm run web`.
- Electron desktop: `src/electron-main.ts` starts the dashboard on an ephemeral loopback port and loads it in a sandboxed window. Packaged runtime data lives under Electron's `app.getPath("userData")`, not the repository.
- The display brand is `乐评寻踪 / MUSIC COMMENT TRACE`, and `productName` is `乐评寻踪`. This is presentation only: keep the technical identity `package name=ncm-comment-finder`, `appId=cn.local.ncm.commentfinder`, repository `RocXOvO/ncm-comment-finder`, artifact stem `NCM-Comment-Finder`, and the persistent Electron directory stable. `electron-main` explicitly pins `userData` to `appData/ncm-comment-finder`; never derive it from the renamed productName, or updates would appear to lose checkpoints and settings.

There is no database. Durable scan state is JSON; matches are append-only JSONL. Generated/runtime directories (`dist/`, `release/`, `.ncm/`, `data/`, `tmp/`) are ignored and must not be committed.

The code version is authoritative in `package.json` and `package-lock.json`. Do not infer a successful GitHub Release from local files; verify the live tag, commit, and assets when releasing or evaluating an update.

## Architecture and data flow

Three scan engines exist and must not be conflated:

1. User-source scan (`scan`, `/api/job`, `runPooledCommentFinder`)
   - Read candidate songs from listening rank (`user_record`), the target user's owned liked-playlist, or both. Liked-song discovery deliberately does not call `likelist`: an authenticated upstream session may resolve that endpoint from the Cookie account instead of the requested UID.
   - Production liked discovery is two independently governed/failover-capable requests, not one Governor call that hides two upstream calls. `getTargetLikedPlaylist` lists `user_playlist(uid)` once (limit 1000) and accepts only `specialType=5` whose `creator.userId` exactly equals the target UID; `getTargetLikedPlaylistSongs` then calls `playlist_detail` and validates the detail owner again. Each step has its own request label/budget accounting and may use a different healthy pool lane. `getLikedSongs` remains the sequential adapter wrapper, and scanners retain a one-call fallback only for alternate/test `NcmClient` implementations that do not expose the two optional methods.
   - Liked-track completeness is strict. Listing and detail `trackCount` values are normalized independently; `null`, `undefined`, empty string, and booleans mean unknown, never numeric zero. If both counts are known they must match, otherwise the catalog is rejected; the detail count is authoritative when present and the listing count is its fallback. `playlist_detail.trackIds` must always be an explicit array, including `[]` for an empty playlist. Every entry must normalize to a song ID, and a known count must exactly equal the returned array length. Count disagreement, missing/malformed IDs, or truncated catalogs fail as 502-style source errors and are never checkpointed; there is no `tracks` fallback. The Cookie authorizes visibility only and must never choose/substitute the source identity. A missing target-owned playlist fails explicitly rather than using the logged-in user's likes. Treat upstream status/code `301` as authentication failure, not proxy failure: fail once with a re-login prompt and never fan the same request across pool lanes.
   - Merge songs by ID while preserving record-first order and source metadata.
   - Page each song through `comment_new` with a descending time cursor, match `comment.user.userId` exactly, and write results. The default page size is 1000 and the accepted range is 1..2000.
   - When `hasMore` is true, the next cursor must be strictly older than the prior cursor. An empty page may still continue when `hasMore` is true and the cursor advances; non-progress or an exception remains recoverable work and must not be reported as complete.
   - `auto` in the CLI may select `user_comment_history` only when the logged-in account UID equals the target. The GUI deliberately uses `strategy: "scan"`.
   - With a verified pool, one lane is created per task-selected distinct egress. Automatic task selection (`maxProxyLanes=0`) uses every verified egress; a positive limit selects only the ordered prefix without changing the shared pool. A song page is one queue item; after a successful page, unfinished songs are requeued so Workers fairly rotate instead of one Worker monopolizing a long song.
   - At pooled-source startup, unfinished songs are pre-sharded round-robin until initial work reaches the smaller of the actual Worker-loop count and the transport gate's current effective capacity, subject to page caps and shard limits. This also expands a resumed song's small set of unfinished persisted shards to the new target by repeatedly splitting the largest remaining cursor range; both split halves preserve that shard's current `pageNo`. Newly sharded cursors inherit the song's current `commentPageNo`, so resume never relabels an unfinished request as page 1.
   - If Workers are waiting after a song cursor advances, that song's unread `[2000-01-01, nextCursor)` range is promoted to non-overlapping half-open `commentShards`. This keeps a one-song source scan and the few-song tail parallel across lanes. Further unread shard ranges use the same adaptive split math as the single-song engine.
   - Source shard IDs are local to a song, so scheduler events include `songId`. `pageInSong` is the aggregate successful-page count across all shards; the UI never substitutes a shard-local `pageNo` for it.
   - `maxCommentPagesPerSong` is an aggregate successful-page cap across a song's cursor and all shards. Per-song permits include in-flight requests; a failed request releases its permit and cannot prematurely mark the song truncated. After the accepted page that reaches the cap, natural end-of-cursor or shard completion is applied first; the song is marked truncated only if uncovered work still remains. The global request budget is reserved separately before dispatch.

2. Single-song parallel scan (`scan-song`, `/api/parallel/job`, `runParallelSongScan`)
   - Read the song metadata, split `[startTime, endTime)` into non-overlapping time shards, newest first, and paginate `comment_new` using descending cursors. One shard page is one queue item.
   - A fresh task materializes only `max(1, min(configured shardCount, actual Worker loops, current proxy-transport capacity))` initial physical shards. This avoids paying one empty boundary request per configured shard when the runtime cannot occupy them. The user-configured `shardCount` is still persisted unchanged as the checkpoint compatibility key; resumes use their persisted shard array, and adaptive splitting may grow that array beyond either initial count.
   - After a page advances, if Workers are waiting, the unread range `[shard.startTime, nextCursor)` is bisected into two non-overlapping half-open shards and both are requeued. The original configured `shardCount` remains the checkpoint compatibility key, while `state.shards.length` and report progress grow with adaptive splits.
   - Failed/cooling lanes return unfinished work to the shared queue for healthy lanes. An adaptive split or failover must never duplicate/skip a time range; JSONL de-duplication is a final idempotency guard, not a substitute for correct range math.
   - Cursor pages are filtered back to the shard's half-open range before UID matching. The endpoint is intentionally called without a login cookie.
   - Dashboard global percentage is cursor-weighted time coverage, computed from the remaining time in every unfinished shard. It therefore survives adaptive splits without the artificial regression caused by `shardsComplete / shards`; it is time coverage, not an estimate of uniformly distributed comments.

3. QQ Music SeqNo scan (`src/qq-music/scanner.ts`, `/api/qq/job`, `runQQMusicScan`)
   - Modes are `song` and `likes`. The requested decimal song ID remains the song primary key; metadata may add MID/name/artists but must not replace it or convert it through JavaScript `Number`.
   - Comment pages use a strictly descending decimal SeqNo, `pageSize=1..25`; public-liked discovery is a separate offset source with `likedPageSize=1..500`. A song has one in-flight SeqNo chain. `likes` may schedule different songs concurrently through the shared fair `LaneAllocator`; the Worker count is hard-capped by `hostConcurrency` without slicing away selected lanes.
   - Every lane has a QQ-policy Governor with pacing concurrency 1. The task owns one profile-derived `QQMusicTransportGate`: song uses one in-flight request and at least 250 ms between starts; likes uses the actual bounded Worker capacity up to 32 and `max(80, ceil(1000 / max(4, capacity))) ms` between starts. This does not change the per-Lane default `3000 ms + jitter` pace. A positive `requestBudget` counts logical comment pages task-wide, not retry attempts or control requests; 0 is unlimited.
   - Proxy requests are fail-closed and never fall back to direct. The shared pool proves egress and NetEase reachability, not QQ-domain reachability. Proxy/network failures may hand the unchanged cursor to another healthy lane; permanent/protocol/source failures, page caps, cancellation, and persistence failures must not be marked complete.
   - QQ durable state/result storage is independent of NetEase source v3. Result de-duplication uses `(songId, commentId)`. The long-lived writer completes `write + fsync` before publishing a match; cancellation is checked again before cursor/state commit. `song` checkpoints each page; `likes` coalesces at 400 ms/4 dirty pages, uses the current transport profile's dynamic pre-request checkpoint-slot count, and awaits any active flush before return. Four is the dirty-page flush threshold, not a fixed transport/checkpoint concurrency cap.

NetEase result flow:

`EnhancedNcmClient` -> scanner -> `JsonlResultWriter` -> JSONL on disk -> optional `onMatch` callback -> server SSE -> `web/app.js` live table. Alongside it, source/parallel request and scheduler activity feed a best-effort `TaskLogger` and the dashboard log view.

QQ result flow is separate: `QQMusicClient` -> `runQQMusicScan` -> `QQMusicResultWriter` -> QQ JSONL -> generation-enveloped Manager event -> SSE/REST -> the matching `qq:song` or `qq:likes` view. Do not generalize the NetEase time-cursor state/writer into QQ SeqNo state.

Song search is lookup-only. NetEase `/api/song/search` uses strict `cloudsearch` song results; both it and the numeric `/api/song` compatibility lookup run through `NcmSongSearchRouter`, rotating a verified running pool without direct fallback and using direct/explicit-proxy behavior only when no pool is active. QQ `/api/qq/song/search` runs through `QQJobManager` so it shares the global QQ lease, `prepareLanes`, cancellation, dynamic song Gate profile and fail-closed proxy rotation without creating or changing a scan generation. Aborting the HTTP lookup propagates to its Manager controller and releases the lease; a newer lookup may safely replace an older lookup, but must never replace or cancel a formal QQ scan. QQ search prefers `DoSearchForQQMusicDesktop`; only a structurally valid empty main list may fall back through the same fetch/proxy/signal to official `smartbox_new.fcg`. A nonempty malformed main response or malformed fallback is a protocol error. Both search routes accept trimmed `q=2..80` and `limit=1..10` and return `{ platform, query, songs:[{ id, mid?, name, artists, album?, durationMs? }] }`; IDs remain strings. Renderer request generations and stale-response rejection are frontend responsibilities, not backend scan state.

`comment_new` success is strict: a non-object/empty/truncated body, non-200 body code, missing object `data`, non-array `comments`, non-boolean `hasMore`, any unnormalizable comment, or `hasMore` without a finite cursor strictly older than the request is a retryable 502-style malformed response, never an empty completed page or cursor advance. Both resolved and rejected upstream responses use numeric `body.code` as the effective status even when HTTP status is 200; sanitized parse/timeout summaries may be logged, but never raw bodies or proxy credentials.

`src/worker-topology.ts` computes the fixed long-lived Worker-loop count shared by both scanners: `min(lanes * workersPerLane, maxWorkers)`; dashboard jobs always pass `hostConcurrency` as `maxWorkers`. Invocation-local IDs are `worker-N`, independent of lane identity. Before each page, every Worker acquires a permit from one shared `LaneAllocator`, whose round-robin cursor spans all selected lanes. A lane can hold at most `workersPerLane` permits, recovering lanes are temporarily ineligible, and unavailable/cooling lanes are skipped. If no lane is currently available but another request is still in flight and may produce a late success, the allocator's `mayBecomeAvailable` predicate keeps waiters alive; only no available lane plus no possible in-flight restoration returns `undefined`. A release, recovery deadline, request settlement/success reset, lane-state change, queue closure, or cancellation wakes waiters. Because a Worker may wait on `queue.take()` after receiving a permit, both scanners recheck blocked/unavailable state and `LaneRecovery.ready` immediately before the remote request; newly-entered backoff requeues the exact work without calling upstream. Request activity carries both Worker ID and the lane actually granted.

Source `JobManager` separates stable scheduled-song visibility from transient requests. `activeSongByWorker` retains each Worker's last scheduled song after a request settles, marking it inactive and clearing its requesting page/start time; the next assignment replaces that Worker's row ownership. `activeSongProgress` is a recency-ordered working set capped at 64 songs: updating a song moves it to the newest position, and trimming evicts the oldest progress-only song while preserving IDs still owned by Workers. Thus recent unfinished songs may remain as zero-Worker waiting rows without letting a large catalog grow the presentation map without bound; active Worker rows remain guaranteed independently by `activeSongByWorker`. Aggregation de-duplicates both maps. A source `done`/truncated progress signal removes that song from both retained ownership and progress; task terminal clears all. The parallel manager publishes its one song from task start through terminal and changes only its active Worker count between requests. Source's legacy-compatible `currentSong` remains aggregate progress only.

The renderer keeps one keyed `activeSongRows` entry per song ID. After a snapshot signature change it removes only vanished IDs, creates only new rows, and updates existing cells/progress in place; identical snapshots do no DOM work. Waiting rows render with zero Workers instead of disappearing, so request boundaries cannot flash the whole table. Active request rows retain their normalized row model, allowing the existing singleton one-second runtime timer to refresh only their longest-wait labels without waiting for the next status poll or rebuilding the table. `null`/missing `requestStartedAt` is normalized to absent before numeric conversion, never epoch zero.

`CheckpointCoordinator<T>` owns the shared live/durable checkpoint mechanics for pooled source and parallel scans only; it does not own scan-domain state. Every opportunity first reconciles external counters, then ordinary live publication uses one leading/trailing 200 ms limiter. An eligible update publishes immediately; updates inside the window mark the state dirty and share one unref'ed timer that publishes the latest cumulative state even if no later checkpoint occurs. Durable snapshots remain independently coalesced (350 ms for pooled source and 500 ms for parallel), are captured with `structuredClone`, and are serialized to disk in capture order. A failed persist rejects that checkpoint call but is removed from the internal tail so later writes can still proceed. Forced terminal/metadata checkpoints cancel any pending live timer, publish immediately, capture a final snapshot, and bypass the disk interval; `dispose()` clears the timer and makes later calls inert. The serial source runner deliberately retains direct per-step persistence rather than using the coordinator. Managers use live callbacks for running dashboard status, so `GET .../job` must not repeatedly read/parse the checkpoint while a task is active and visible counters may legitimately lead the last durable file. Disk state remains authoritative for resume and may be read once to reconcile a terminal snapshot. Status callbacks are best-effort presentation and must never affect persistence or scheduling.

`JsonlResultWriter` owns serialized append-only persistence and de-duplicates by `commentId`, including IDs already on disk. Its startup scan streams JSONL in 64 KiB chunks and periodically yields to the event loop; do not restore a whole-file `readFile().split()` path that can stall Electron when results are large. `ResultAccumulator` is the single checkpoint-local accounting boundary used by serial source, pooled source, and parallel scans. If the checkpoint already owns an ID, the record is ignored without touching JSONL. Otherwise it awaits the writer first, then rechecks its checkpoint-local set so concurrent duplicate observations count only once; a row found in pre-existing JSONL is not appended again but is added to a fresh checkpoint exactly once. An append failure must leave `seenCommentIds` and `matchCount` unchanged. Do not seed a new checkpoint with every historical output ID: ownership transfers only when the scan actually rediscovers that match. SSE/UI failure must never interrupt persistence.

Full-result reports deliberately use a different read path from bounded dashboard tails. `readJsonlSnapshotDetails` opens the append-only result file, captures its exact byte size, and streams only `[0, size)`; later appends are excluded, while missing files, blank lines, and an incomplete/malformed trailing record yield a safe empty/partial snapshot. Report generation has explicit 64 MiB/20,000-record memory guards and fails visibly with 413 instead of truncating or exhausting Electron. The loopback route validates `platform + mode + jobId + targetKind + target`; legacy `uid` query input remains NetEase-only compatibility. NetEase binds a numeric UID; QQ binds canonical EncryptUin plus its internal output path, with checks before and after asynchronous reads. HTML escapes every scanned/user field and rebuilds only trusted platform links from numeric NetEase IDs or validated QQ MID/decimal song ID. The Electron export DTO is a discriminated union and the hidden window rechecks all five identity fields after fonts are ready; diagnostics redact the QQ target and proxy credentials.

Song identity is a domain concern, not renderer decoration. Listening-rank entries normally include names, but liked-playlist `trackIds` supply IDs only. `EnhancedNcmClient.getSongInfos` de-duplicates IDs and calls `song_detail` with comma-separated IDs; `hydrateMissingSongMetadata` first builds one `missing song ID -> candidate references` map, then processes its IDs in batches of at most 500 without rescanning the full candidate list per batch or disturbing source/discovery order. Each successful batch updates only its indexed candidate references immediately. If a later batch fails, the scanner counts the already-applied names and still forces a checkpoint, so partial metadata work survives while remaining IDs retain their fallback. Serial and pooled source scans run this hydration after discovery and when resuming older unnamed checkpoints, persist newly found names/artists in the existing state, and publish the catalog to `JobManager`. Its in-memory ID/name map enriches source SSE and result-list rows when needed. Metadata failure is non-fatal except cancellation, must retain an ID-based fallback, and must never become renderer-side per-row/per-poll requests.

## Task snapshots, live progress, and terminal settlement

The dashboard keeps independent source, parallel, and QQ snapshots, but a shared `TaskCoordinator` permits only one active source, parallel, QQ, or pool task at a time. `GET /api/tasks/active` and `POST /api/tasks/stop` are the authoritative global update-install boundary. Every accepted `POST .../job` receives a new UUID. The renderer polls snapshots about every 1.5 seconds while result rows arrive independently over SSE. Status polling is single-flight (never overlapping), slows while the document is hidden, and resumes immediately when visible.

Dashboard state is keyed by the complete view: `netease:parallel`, `netease:source`, `qq:song`, `qq:likes`. QQ public generation is `{platform, mode, jobId, target:{kind:"encryptUin",value}}`; the Manager's internal generation additionally binds state/output paths. Results, logs, SSE, settlement, export, and estimator guards must compare the complete generation/view, not only `mode` or a shared `qq` bucket. QQ request/resume input uses `workersPerProxy`; scanner/snapshot internals use `workersPerLane`. Stable snapshot topology fields are `targetLabel`, `configuredLanes`, `configuredWorkers`, `participatedLanes`, `participatedWorkers`, and `peakInFlight`.

Renderer button disabling during pool selection is only UX. `TaskCoordinator` leases and HTTP 409 responses are the authoritative mutual-exclusion boundary. Every renderer path that changes task availability must converge through `syncTaskStartAvailability`; individual render functions must not independently re-enable a start button.

- Result descriptors are generation-consistent. Source start computes local next state/output paths, completes every awaited preflight, then publishes `statePath`, `outputPath`, and the snapshot job ID synchronously with no intervening `await`; a rejected start leaves the previous result descriptor intact. Source and parallel `results()` capture `jobId` plus `outputPath` before awaiting the JSONL read, and source also clones its song-name map, so one response cannot mix generations. Full reports add an explicit expected-`jobId` boundary: never export whatever file happens to be current after a mode/task switch.
- `activeSongs` is an unfinished-song presentation, not a raw in-flight request list or completion authority. It de-duplicates Worker-retained scheduling with at most 64 recent source-progress rows; `workers` is the instantaneous active count and may be zero. A recent source row with known progress can remain visible while temporarily unowned, while an older inactive row may be evicted from presentation before completion; `done`/truncated and task terminal still remove authoritative retained state. Source `pagesProcessed`/`pageInSong` counts only successful pages. Its one-based `requestingPage` belongs to each active shard/request; a song row shows their minimum and clears it when no request remains without discarding successful progress. Request `start` carries an ISO `startedAt`; each manager exposes the earliest active start for that song as epoch-millisecond `requestStartedAt`, clearing it when no request remains. Missing or invalid server timestamps fall back to `Date.now()`, and renderer nulls remain absent rather than becoming zero. Each row may also carry `commentsProcessed`, `totalComments`, and `progressPercent`; source percent is comments/known total. The single parallel song sets `progressBasis: "time"` and uses split-stable cursor-weighted `coveragePercent`: that percentage is time-range coverage, never total-comment completion, even when `totalComments` is known.
- Checkpoint counters remain authoritative for durable progress (`songsProcessed`, pages/shards, requests, and matches). In pooled source and parallel scans, `CheckpointCoordinator` mirrors the newest in-memory counters with leading/trailing publication at most once per 200 ms, without a hot-path disk read and even when the durable write is skipped by its separate coalescing interval. A trailing timer must publish dirty state without needing another page; force must cancel it before immediate final publication and capture the final state independently of later mutations. Request activity may be newer still, but neither callback nor the coordinator may mutate checkpoint cursor semantics. Result counts change only through `ResultAccumulator` after writer persistence succeeds or confirms that the row already exists.
- The workspace has one task-total progress bar. Source global progress is completed songs over selected songs; parallel global progress is cursor-weighted time coverage. The central `activity` output tab separately lists stable scheduled songs and their current active Worker counts without inventing per-song completion. `totalComments` remains optional scanner/report data, and `mergeCommentTotal` keeps the maximum of stored total, latest credible total, and processed count; UI percentages never determine task completion.
- Both snapshot shapes expose the same task-timing contract: `startedAt`, optional `finishedAt`, and non-negative `elapsedMs`. While status is `running`/`stopping`, elapsed time is `now - startedAt`; after a terminal transition it is frozen at `finishedAt - startedAt`. Polling a finished task must not keep increasing its duration.
- `finishedAt` is assigned once when the manager settles a report or error. Use the manager's snapshot timestamps for UI timing in both modes rather than mixing them with scanner-local report timers, which start at slightly different points.
- The renderer's single runtime clock is resynchronized from the active snapshot on each accepted poll, then advanced with `performance.now()` once per second only while status is `running`/`stopping`; it skips identical text and freezes at the terminal value. That same interval refreshes each active song's `最长 ...` request age from the earliest `requestStartedAt`; do not create timers inside render functions, and clear the singleton timer on `pagehide`.
- Both managers reset a `CommentRateTracker` per job and feed it only page activity published as successful after descending-cursor validation, using the actual returned comment count. Snapshot `commentsPerSecond` is the one-decimal rolling rate over at most 10 seconds (minimum one-second observation), decays to zero when no successful comments remain in the window, and is forced to zero after the job stops. Invalid cursors publish `failure` status 502 and never inflate rate or progress. This is measured throughput, distinct from matches, requests, estimates, and durable progress.
- Combined job/pool refreshes are single-flight: timer, visibility, mode-switch, and manual refresh triggers share the same pending Promise, so an older overlapping poll cannot roll progress, status, pool state, or the runtime clock backward.
- Repeated identical job and active-song snapshots do not rewrite their DOM. SSE matches are buffered into short render batches and the visible-result map remains bounded. Result APIs return the descriptor's captured `jobId`; a changed job generation clears old rows. During one snapshot request, newly arrived SSE IDs stay first, followed by the snapshot's newest-first order and then retained older IDs, without sorting by historical comment time. A high match rate must not rebuild the whole results table once per comment. The log tab refreshes at most about every three seconds and skips identical table payloads.
- Dashboard-terminal statuses are `complete`, `matched`, `paused`, `cooldown`, `dry-run`, `stopped`, and `error`. `idle`, `running`, and `stopping` must not produce a settlement screen. Paused/cooldown/stopped are resumable but still end the current invocation and therefore get a settlement.
- The task-end settlement UI is keyed by scan mode plus snapshot UUID and opens at most once for that task, even though polling repeatedly renders the same terminal snapshot. Starting a new UUID clears the prior task's presentation state; dismissing a settlement must not let the next poll reopen it.
- Settlement values come from the terminal snapshot: duration from `elapsedMs` and total hits from `matches`. Never derive hits from the renderer's visible-result map, which is capped and mode-local. `matches` is checkpoint-cumulative across resumptions; `elapsedMs` is for the current UUID/invocation. If product copy ever promises cross-restart cumulative runtime, add a persisted duration field to the state schema instead of relabeling this value.
- The settlement is a presentation layer over the existing task/results view: results stay persisted and accessible, zero matches is a valid successful outcome, and error/cooldown notes remain visible. Render server text with `textContent`, give a dialog/overlay correct focus and close behavior, and honor `prefers-reduced-motion`.
- Preserve behavioral tests for live/frozen elapsed time, progress math, scanner checkpoint callbacks, Worker-keyed activity, discovery-order rendering, stale-refresh rejection, and renderer settlement de-duplication; a static HTML text assertion alone is insufficient evidence.

## Concurrency and rate-control invariants

- A lane is one client/proxy endpoint plus one `RequestGovernor`; every proxy-backed lane in one scan also shares the task's `ProxyTransportGate`.
- `workersPerLane` (HTTP/resume name: `workersPerProxy`, UI label: "每出口工作线程") is a per-lane upper bound, not a promise to create that many resident loops for every lane. Raw topology capacity is `lanes * workersPerLane`; actual dashboard Worker loops are `min(raw capacity, hostConcurrency)`.
- The governor serializes request **start slots** per lane using `ceil((minDelayMs + random jitter) / workersPerLane)`; requests already in flight may overlap. The configured per-IP concurrency therefore increases that lane's start rate while preserving one shared scheduler for the IP.
- `hostConcurrency` is the configured per-task hard ceiling for actual Worker loops and for proxy transport, accepted by source/parallel start and estimate APIs as `1..32` with default 8. Direct/static-proxy source jobs use the same Worker ceiling. The shared proxy `ProxyTransportGate` starts at that ceiling, with 80 ms plus 0..40 ms jitter between first-hop starts. Three transient failures (undefined status, 408, 425, or 5xx) within 10 seconds halve the effective transport ceiling (`18 -> 9`, floor `min(4, configured)`) and scale the base start interval by `configured/effective`. After at least 20 successful gated requests and five seconds since the last adjustment, it restores one transport slot at a time. AIMD does not destroy Worker loops; retries reacquire the gate, waits do not hold transport capacity, and snapshots expose `proxyTransportEffectiveConcurrent` separately.
- Topology settings travel through the full runtime path: toolbar form -> source/parallel payload -> server validation -> fixed Worker count/shared LaneAllocator/gate construction -> snapshot/log/resume -> toolbar and estimator. Snapshot/report/log `workers` is the actual bounded Worker-loop count, not the raw lane product. The renderer shows selected/available exits and active/actual Worker counts, and warns only when raw topology capacity is below the host ceiling.
- Managed-pool capacity and per-task exit selection are separate. `maxProxyLanes` accepts `0..32`: `0` automatically selects all ordered verified exits; a positive value caps the task subset, always bounded by availability. Its selection metadata records requested versus actual lanes. Even when there are more exits than Worker loops, every selected healthy lane remains reachable because all Workers share one round-robin allocator; the host cap must never be implemented by dropping later exits. Static-proxy/direct source scans still use one lane and do not shrink or rebuild the shared pool.
- `estimateCommentScan` models independent pagination partitions instead of pretending all comments occupy one perfectly packed global page stream. Without runtime calibration it distributes the aggregate count across partitions, sums `max(1, ceil(partitionComments / pageSize))`, and therefore avoids a `100 -> 200` page cliff when one partition barely crosses a boundary; an explicitly empty partition still costs its discovery request. With calibration, page count is at least one per partition and otherwise follows measured effective comments per successful page. Estimated request count inflates page count by the observed remote-attempt success ratio. Raw `totalWorkers` remains `lanes * workersPerLane`, while `effectiveWorkers` is bounded by `maxWorkers` and the current `proxyTransportEffectiveConcurrent`; reported effective transport start spacing scales by configured/effective capacity exactly as AIMD does.
- `PagePerformanceTracker` resets per source/parallel UUID. Each terminal activity distinguishes logical pages from actual remote attempts, sums only time inside the upstream client call (excluding Governor/gate queue, spacing, and retry backoff), and measures fill from comments that belong to the page's effective time shard. The GUI may calibrate only for the same target, song, page size, delays, per-lane workers, lane count, host ceiling, source/shard configuration, after at least three completed logical pages with at least one successful nonempty-page average. It then shows both page and attempt counts and uses network time per attempt, effective fill, remote-attempt success ratio, current AIMD concurrency, and effective start interval; before that threshold it labels the estimate theoretical and uses pool probe latency. Parallel partitions are capped to the smaller of configured shards, actual Workers, and effective transport capacity, matching fresh-task physical sharding. These estimates remain planning aids, not completion or retry guarantees.
- GUI request budget `0` means unlimited. A positive pooled budget is enforced by the shared scheduler for comment-page reservations; source discovery happens before that reservation, and governor-internal retries do not consume the aggregate reservation, so this is not an absolute hard limit on every actual HTTP request. This is a known follow-up optimization point. CLI `scan` uses the governor budget directly.
- Every `EnhancedNcmClient` request carries a 30-second upstream timeout by default. Network/`5xx`/408/425 failures first receive bounded Governor retry; a final ordinary lane failure requeues the exact work and applies exponential 1..30 second `LaneRecovery`. Five consecutive final failures mark the lane unavailable, but source and parallel scanners track `activeLaneRequests` and do not declare total exhaustion until all in-flight lane work settles. A late success resets recovery, removes the unavailable mark, and `recordSuccess()` wakes Workers waiting on the obsolete backoff. Cooldown supersedes ordinary unavailability. Determine exhaustion with `lanes.every(blocked || unavailable)`, never by adding set sizes; mixed/repeated-failure exhaustion settles as `paused`, while all-cooldown remains `cooldown`. Required work uses `RequestGovernor.execute`; optional enrichment uses non-poisoning `executeBestEffort` without weakening required `403/429` behavior.
- Each task Manager owns an `AbortController`. Stop aborts the scanner signal and cancels Governors/gate; the scanner listener closes the queue, cancels every `LaneRecovery`, and wakes other internal waiters before another remote start. Default recovery timers are cleared when cancellation wakes them. Remove the abort listener at scanner exit and clear the controller on all setup/terminal paths.
- Pooled metadata hydration creates one local session per hydration run with a rotating `nextLaneIndex` and a local `cooldownLanes` set. Successful batches advance the starting lane so healthy metadata-capable exits share work. A `CooldownRequired` marks that lane only in this optional session and later metadata batches skip it; ordinary failures may try the next lane but are not permanently skipped. This local set must never be reused as, copied into, or allowed to mutate the pooled comment scanner's correctness-critical `blockedLanes`; the non-latching Governor policy alone is not a substitute for that scope separation.
- `AsyncWorkQueue` is the pooled scanners' completion detector: `take()` waits while work remains in flight; every taken item calls `complete()` exactly once; `stop()` wakes waiters and rejects requeue. Each scanner registers exactly one `whenClosed()` continuation that cancels all lane recoveries; Workers await recovery normally, then check `isClosed()` before taking work. Do not create one closure reaction per page/Worker. Queue removal uses an amortized O(1) head cursor and compacts only after at least 1,024 consumed slots and half the backing array; preserve FIFO across compaction/requeue and never restore repeated `Array.shift()`.
- The global `TaskCoordinator` lease is released idempotently on setup failure and in each async task's `finally`. Pool build/import/stop and background rechecks must not overlap an active scan, and source/parallel scans must not run together in the dashboard process.
- Do not use routine tests to create high real-world traffic. Unit/integration tests use stubs and loopback servers; real NetEase or proxy-pool checks must be explicit and low-risk.

## State, checkpoints, and coverage

- `src/state.ts` owns source-scan state. Source/parallel state, the GUI resume descriptor, and proxy-pool status all use `src/atomic-file.ts`: same-directory unique temporary names, fsync, and bounded `EPERM`/`EBUSY`/`EACCES` rename retry. A failed final rename never deletes the formal file and leaves the completed temp recoverable. Reads skip only unreadable/malformed JSON while choosing the newest syntactically complete formal/new-style/legacy candidate; once parsed, its decode/schema result is authoritative and failure must never fall back to older state. Proxy-pool recovery is covered explicitly because an interrupted rename must not lose managed-process identity.
- Current source state is version 3 and records `commentPagination: "cursor-v1"` and `commentPageSize`, plus UID, strategy/source/scope, candidates, per-song cursors/page counts/optional `commentShards`, seen IDs, request/match totals, truncation, source errors, cooldown, coverage, and the last catalog reconciliation counters. Version-1/2 state is upgraded when an explicit path is read; changing page size requires `--fresh` (or a new state path). Dashboard and CLI defaults use target-v3 paths, so they never discover old state merely because it exists beside the new path.
- Candidate names/artists are optional fields in the existing source-state schema. Metadata hydration updates each successful batch in place and forces a checkpoint when discovery or any hydration batch changed the catalog, even if a later optional batch failed. Old unnamed liked-song checkpoints therefore gain and retain partial titles without a state-version bump or source rediscovery.
- Legacy offset checkpoints are migrated only by safely rescanning songs that were unfinished or truncated: each starts at the task's immutable `createdAt` cursor, and JSONL `commentId` de-duplication makes the intentional overlap idempotent. Completed, non-truncated songs are not rescanned merely for migration.
- `src/parallel-scanner.ts` owns `kind: "parallel-song"`, version 1 state with immutable scan range/shard/page-size identity plus per-shard cursor and counters. Writes are coalesced to about 500 ms and forced at task end.
- Adaptive child shards are appended to and persisted in the same parallel checkpoint with fresh monotonically increasing IDs. Resume loads that expanded shard list; it must not reconstruct only the original configured shard count.
- Source song progress and parallel state may persist optional `totalComments`. Pooled and serial source runners both consume unfinished source shards, so changing entry shape never silently restarts the pre-split cursor range. In both source and parallel scanners, comments without a usable `time` are inspected and assigned to the shard response that returned them rather than dropped; cursor-boundary math uses only finite timestamps, and `commentId` de-duplication guards repeated delivery. Parallel `coveragePercent` is derived from persisted shard bounds/cursors at status time rather than stored as a compatibility field.
- Reusing state with a different UID/source/scope/strategy, source cursor page size, or parallel range/shard/page-size is rejected. Use `--fresh` or a new state path.
- Source state carries `sourceCatalogVersion`, currently `SOURCE_CATALOG_VERSION=3`. Compatibility rejects a `likes`/`both` checkpoint without that exact catalog version, including an explicitly supplied CLI state path, because an older catalog may contain the Cookie account's likes rather than the target UID's.
- Dashboard source paths are an explicit target-v3 boundary: every source gets `web-state-{uid}-{source}-target-v3.json`; all three sources for one UID share only `web-comments-{uid}-target-v3.jsonl` and `web-song-coverage-{uid}-target-v3.json`. Never probe/import target-v2 likes/both paths or the unversioned legacy record/shared result into trusted v3 coverage. Old files remain untouched for manual archival. A future storage-semantic change must bump `SOURCE_CATALOG_VERSION` and all derived state/result/coverage suffixes together.
- Every modern non-fresh source run refreshes the selected upstream catalog before deciding a finished checkpoint can return. Reconcile strictly by `song.id`: current catalog order/metadata may change, but existing `done`, cursor/page, shards, totals, and counters remain attached to the ID; genuinely new IDs receive a new current-time cursor. Retain removed historical entries rather than destructively deleting progress. A failed refresh retains the previous full catalog and reports `sourceErrors`; a partial `both` refresh unions successful metadata with prior entries and must not shrink the previous catalog count.
- `src/song-coverage.ts` owns the v3 per-UID complete-song ledger. Only naturally exhausted songs without catalog/source errors, catalog truncation, page caps, truncated IDs, or incomplete shards may enter it. Ledger read-modify-write is protected by a cross-process `proper-lockfile` lock and uses `writeAtomicJson`; never replace it with a fixed sibling temp or unlocked last-writer-wins save. UID and schema mismatches are hard errors. Cross-source reuse marks the current mode's progress complete and relies on the canonical per-UID JSONL so old hits remain visible in live results and full reports.
- `--fresh` ignores the selected checkpoint and bypasses coverage-ledger skipping, so it intentionally rescans the selected catalog. It does not clear the target-v3 canonical JSONL, whose writer continues to de-duplicate `commentId`. Generic CLI custom paths are explicit caller choices; defaults carry the v3 suffix and a per-UID coverage path.
- `coverageComplete` is true only when all selected work finished without source failures or configured truncation. A task may have status `complete` while coverage remains incomplete. Source snapshots and settlement must separately expose catalog total, historical completion, coverage reuse/skip count, and new pending count so a zero-comment-request incremental run is not presented as doing nothing.
- GUI tasks intentionally force `stopAfterFirst: false` so scanning continues until completion, cooldown, budget, failure, or manual stop.
- `data/resume-task.json` is a separate version-1, atomically written descriptor containing the most recent accepted GUI mode and non-sensitive primitive form parameters, including `maxProxyLanes` and `hostConcurrency`. It is not a checkpoint and never replaces state compatibility checks; topology used by a prior invocation is not scan-state compatibility. Save failure is logged but must not stop scanning or checkpoint persistence.
- `GET /api/resume` returns `{ task: descriptor | null }`. At boot the renderer restores only an explicit per-mode allowlist, forces both `fresh` controls off, and waits for the user to start; it never auto-runs a recovered task. Unknown descriptor versions/malformed JSON are ignored safely. Because Electron keeps `userData` across installation, the descriptor restores parameters across versions while the existing scan JSON restores cursor/shard progress.

## Structured task diagnostics

- Each accepted GUI run writes `data/logs/{source|parallel}-{uuid}.jsonl`; packaged Electron resolves this under `userData`. Entries contain `timestamp`, `level`, `event`, `mode`, `runId`, a human message, and optional structured details.
- Stable event meanings are `task_started`, `task_finished`, `task_error`, `page_start`, `page_success`, `page_failure`, `rate_limited`, `adaptive_split`, and `resume_descriptor_failure`. Request details may include lane, song/page/shard, elapsed time, count, `hasMore`, and remote status; never include Cookie, proxy credentials, tokens, or raw private configuration.
- `TaskLogger` serializes appends. Callback/logger failures are deliberately swallowed: diagnostics must never affect request scheduling, checkpoints, results, status, or coverage.
- `GET /api/logs?mode=source|parallel&limit=N` reads the current snapshot's log path, newest first. Log and result-list endpoints use `readJsonlTail`, scanning backward in 64 KiB blocks only until the requested number of newest nonempty lines is reached, then skipping malformed JSON. This bounded UI read does not replace `JsonlResultWriter.initialize()`'s full-file ID scan for durable de-duplication. Old files persist locally but are not an arbitrary-path API; the renderer uses `textContent` for untrusted diagnostics.

## Proxy-pool design

`src/mihomo-pool.ts` supports two pool sources:

- Clash Verge: discover its merged config/profile YAML and `verge-mihomo`; accept one or more allowlisted profiles; validate, fairly interleave, de-duplicate, and conflict-rename inline leaf nodes; generate one config/process/controller with one loopback mixed listener per candidate; then verify it. Provider-backed or chained nodes are rejected explicitly because their relative/cache/reference semantics cannot be safely flattened.
- External: normalize supplied HTTP/HTTPS proxy URLs and verify them directly; no managed PID is required.

Verification has two gates: query the public egress IP, then call a real NetEase comment endpoint. Entries are sorted by combined IP-check and NetEase latency, de-duplicated by real egress IP, and only verified distinct IPs survive. Scans re-verify an active pool at task start.

Dashboard scan starts are fail-closed for proxies. Parallel mode requires a running, fully reverified pool. Source mode requires that pool or an explicit static proxy; without either it rejects the start unless the user explicitly enables `allowDirect`, which is saved in the non-secret resume descriptor. An expected pool that fails verification never silently falls back to direct. `/api/song` and `/api/song/search` use `NcmSongSearchRouter`: an explicit proxy wins; otherwise an active verified pool rotates the starting exit and tries at most three transiently failing exits, never falling back to direct, while no active pool uses direct once. `/api/user` similarly uses `UserProbeRouter`: an explicit proxy wins; otherwise an active managed pool rotates the starting exit per lookup and tries at most three verified exits for transient failures, never falling back to direct after a pool failure. A preserved terminal 404 is reported immediately as a missing/inaccessible UID rather than rotating every exit; `RequestGovernor` must retain non-retryable upstream status on its terminal wrapper for this classification. With no active pool the router uses direct once and returns an actionable localized error. The public `user_detail` request deliberately omits the operator cookie so an expired session cannot break a public UID switch; record/target-likes probes retain the cookie where useful. CLI proxy behavior remains explicit to each command.

Managed pool selection treats an IPv4 `/24` or IPv6 `/48` as one network: only the fastest verified entry from each network may be selected, and a requested managed size must be filled. External import treats `size` as an upper bound and succeeds with at least one verified entry. While a pool is running and no coordinator lease is active, dashboard status schedules a non-overlapping background recheck about every 60 seconds; successful full rounds persist fresh latency/IP data and a temporary failure keeps the last known-good entries for a later retry.

The frequently-polled pool status route uses only the managed PID's cheap liveness signal and caches Clash Verge discovery for about 30 seconds. It must not spawn `ps`/PowerShell or reparse profile YAML on every renderer poll. Managed lifecycle checks classify the saved PID as `not-running`, `verified`, `mismatch`, or `unavailable`: `verified` requires the saved executable and exact generation-config path in the command line; `mismatch` proves the live PID is not that managed generation; `unavailable` means the OS command line could not be read. Start/stop use the asynchronous query path; Windows gives raw CIM/PowerShell output up to six seconds, then falls back to `wmic.exe` for up to two seconds. The synchronous two-second identity path remains only for bounded read decisions such as managed-pool cache eligibility, never the frequent status poll.

Managed start/build, stop, and external import are serialized across clients with `proper-lockfile`, keyed by the exact pool descriptor path rather than a separately supplied work directory. `realpath: false` permits the first build before the descriptor exists; the lock has no retries, a two-minute stale threshold, and a 20-second heartbeat. A competing holder fails explicitly instead of waiting invisibly. Refresh performs its slow network probes outside the lock, then takes this same descriptor lock for the final generation compare-and-swap and atomic write, so every authoritative pool mutation shares one lock domain without holding it through the minute recheck.

Each managed attempt gets `generations/{timestamp}-{uuid8}/` with its own `config.yaml` and `mihomo.log`, a random controller secret, and a dynamically selected free contiguous listener segment plus controller port. Listener count follows the candidate count, not merely the final selected-exit count. The generation ID, exact config/executable paths, listener/controller ports, controller secret, PID, and any management notice are persisted in the private atomic pool descriptor; external imports also receive a unique generation ID. The controller secret is not exposed by the pool-status API.

Replacement is new-before-old. The new generation starts beside the old one, passes listener, public-egress, distinct-network, real-NetEase, PID-liveness, and executable/config identity checks, and becomes authoritative through the atomic pool-file write before old cleanup begins. A temporarily `unavailable` command line is tolerated only after the child is still live and all network checks passed; `not-running` or `mismatch` never switches the descriptor. When an older managed PID exists, the handover has a second post-commit/pre-cleanup health gate: `managedGenerationHealthy` requires the new PID alive before and after probing and every selected listener endpoint accepting a connection. If that gate fails, the previous descriptor is atomically restored and an error is thrown; the common failure cleanup then signals and briefly waits for the new child, while the old PID has not yet been signalled. Because building may take tens of seconds, old-process ownership is also queried again immediately before this cleanup boundary instead of trusting the identity observed at build start. Only cleanup-time `verified` is signalled; cleanup-time `mismatch`/`unavailable` is preserved. Failure to kill or observe old exit within five seconds does not roll back the healthy new pool and instead persists a management notice. A successful verified cleanup or cleanup-time `not-running` explicitly removes any provisional/stale notice. Stop still kills only `verified`, requires confirmed exit before persisting inactive state, refuses `unavailable` without changing state, and treats `mismatch`/`not-running` as stale bookkeeping that can be marked inactive without signalling that PID. Management notices flow through `/api/pool` into the build toast and the degraded-but-running pool label.

Task-start reuse of the 90-second managed-pool cache requires full executable-plus-config identity, along with live/active state, NetEase verification, and distinct networks; `unavailable`/`mismatch` therefore falls through to live listener/egress verification instead of trusting cached entries. The minute background refresh deliberately uses cheap PID liveness plus full endpoint rechecks and stable saved egress IPs, and must not launch synchronous CIM/PowerShell. After a slow refresh, it writes only when the current descriptor still has the same generation ID (or the legacy source/time/PID/config fallback key); if a build/import replaced the pool meanwhile, refresh returns the newer generation untouched, and a stopped pool still fails. External pools do not have a managed identity requirement.

Focused proxy evidence covers the four identity states, fallback port allocation, refusal to claim a live PID exited, new-PID/all-selected-listener handover health, same-target lock serialization/reacquisition, refresh generation CAS, reused-PID kill protection, and dashboard pool/runtime wiring. It still lacks an end-to-end fake-Mihomo rollback test that observes descriptor restoration plus old/new process outcomes, as well as generation layout/secret persistence, cleanup-time identity changes and cleanup failures; it also lacks cross-process heartbeat/stale-lock behavior, stop/import-versus-refresh contention, port exhaustion/races, async CIM-to-WMIC fallback, and management-notice clearing/rendering assertions. Generation directories are not yet retired after failed builds, replacement, or normal stop; uninspectable/mismatched and verified-but-unkillable old processes have no later ownership-aware reaper. A failed post-spawn build signals its child and waits only two seconds best-effort. Port probing checks availability but does not reserve the segment against an unrelated process racing the subsequent spawn. Process ownership remains executable-plus-config command-line matching rather than a creation-time/nonce fingerprint.

Default managed pool: 8 selected exits from 48 candidates, listeners beginning at port 17891, controller on 19097. The dashboard exposes both counts (selected exits 1..32, candidates 1..128); these are defaults, not assumptions for scan logic. Startup listener probes use at most 16 concurrent waits and share one 15-second deadline across every bounded batch; queued ports never receive a fresh timeout.

Security rules:

- Generated listeners bind only to `127.0.0.1`; LAN, TUN, IPv6, and DNS are disabled in the generated Mihomo config.
- Clash profile paths accepted by the dashboard must be in one cached discovery allowlist; one to 32 paths may be selected. `readClashVergeProfiles` additionally confines profile files to the profile directory and accepts only YAML remote/local entries. All selected YAML and the new generation's `mihomo -t` validation must pass before replacing a live managed process.
- Proxy URLs may contain credentials. Atomic pool files acquire mode `0600` on their completed temporary inode before rename, so there is no post-commit `chmod` race; generated configs are also restricted off Windows. Dashboard responses mask credentials, and logs/errors must not expose them.
- Scan traffic starts under the configured `hostConcurrency` ceiling and 80..120 ms aggregate spacing, then AIMD may lower effective concurrency and lengthen the base interval after clustered transient failures. Pool build/import/verify/refresh retains its separate 4-request/80-ms gate. These controls reduce burstiness but cannot hide the host IP from the upstream proxy provider or guarantee that a provider will never rate-limit the account; low latency is a health signal, not stealth.
- Task startup may reuse pool entries checked within the last 90 seconds only when the pool is still marked running, every entry is NetEase-verified, and all egress networks remain distinct. Stale or inconsistent entries still require full live verification; this avoids making every Start click repeat the background pool recheck.
- Never commit or print `.ncm/cookie.txt`, QR images, proxy-pool files, profile contents, tokens, `.env`, or user result/state data.

## Desktop and updates

- `src/electron-main.ts`: app/window lifecycle, loopback dashboard, navigation restrictions, IPC handlers, and Windows updater initialization.
- `src/electron-preload.ts`: the only renderer bridge. Keep `contextIsolation: true`, `nodeIntegration: false`, and `sandbox: true`; expose narrowly scoped methods only.
- `src/window-shell.ts`: frameless Windows policy, desktop URL marker, and shared IPC channel constants. The sandboxed preload duplicates channel strings intentionally because it cannot require local modules at runtime.
- Results PDF export is a narrow IPC capability, not general renderer filesystem or print access. The main process accepts it only from the current main window, rejects non-object/array input, validates `mode`, UUID `jobId`, and numeric UID, then acquires one in-progress guard before opening the save dialog so overlapping dialogs/renders cannot race. A hidden child `BrowserWindow` created inside the guarded `try` has `contextIsolation: true`, `nodeIntegration: false`, and `sandbox: true`, denies new windows, and blocks navigation away from the exact generation/UID-bound loopback report URL. After `loadURL`, export waits for `document.fonts.ready` and verifies both report job and UID meta before A4 `printToPDF`; the buffer uses the shared unique-temp/fsync/Windows-rename-retry atomic writer and the window/guard are always cleaned up. Long comments are split into lossless continuation rows, and each conservative print-page group is rendered as a separate table so Chromium cannot overlap rows at a page boundary and every continued page gets a full header. Do not expose arbitrary URLs, filenames, paths, HTML, or print options through the bridge.
- Browser mode uses the same `/report/results` route in a new `noopener` window and `web/report.js` provides the explicit `window.print()` action. This is a fallback to the browser's print/save dialog, not permission to weaken the Electron IPC boundary or CSP.
- Renderer navigation/popups are denied and opened via the OS external browser. Static responses set a self-only CSP and prevent path traversal.
- `src/update.ts`: generic GitHub latest-release lookup and platform asset selection for web/macOS/manual fallback; API responses are cached for five minutes by the server.
- `src/windows-updater.ts`: packaged-Windows-only state machine around `electron-updater`. Auto-download/install are off; the UI checks and downloads with progress/integrity verification.
- Before installing a downloaded Windows update, `web/app.js` identifies the globally active scan, calls its stop endpoint, and polls every 250 ms until the status leaves `running`/`stopping`. Cancellation stops new queue scheduling and wakes Governor, transport-spacing, and lane-recovery waits; task exit then forces its final checkpoint. QQ lookup controllers are tracked as a set: while any lookup is still settling, `qqLookupBusy` keeps task starts and direct update installation disabled, and an older lookup's `finally` cannot clear a newer lookup's protection. Only after these barriers clear may the renderer invoke silent restart/install. A 45-second timeout or any stop/status error cancels installation rather than risking an unconfirmed checkpoint.
- Release notes received from `electron-updater` are normalized into readable plain text before being sent to the renderer. This is intentionally defensive: GitHub-authored HTML such as headings/lists and encoded entities must never render as literal markup in the update dialog.
- `electron-updater` is loaded lazily only when packaged Windows initializes native updates. Never use its nonexistent default export, and keep updater initialization failure non-fatal so the dashboard can fall back to manual release checks. Desktop startup/updater/renderer failures are written under `userData/logs/desktop.log`.
- Windows auto-update releases require all three matching artifacts: the NSIS `.exe`, its `.exe.blockmap`, and `latest.yml`. The metadata names/version/hash must match the final installer. A client older than the first updater-capable release still needs one manual upgrade.

## README factual contract

The README may be reorganized or shortened, but a rewrite must preserve these user-visible truths and must not turn estimates or external release state into guarantees:

- The target is a numeric NetEase user UID. The dashboard has an adjacent UID tutorial; the ID comes from the user's profile URL, not the nickname.
- For another user, the app discovers candidate songs from public listening rank and/or the target UID's owned `specialType=5` liked-playlist, then matches normalized comment author IDs exactly. Login may authorize playlist visibility but never changes the target owner; list and detail owner checks reject Cookie-account substitution. Playlist discovery and track loading are separately governed requests. The detail must contain explicit `trackIds`; known list/detail counts must agree and match its length, while `null` remains unknown rather than becoming zero. Any violation is rejected instead of silently reducing coverage. Logged-in self lookup may use comment history. Source visibility still depends on privacy settings and login state.
- The user preview reports listening-rank and target-owned liked-song counts separately for a fresh probe. A `both` task reports the record-first, song-ID-de-duplicated union, so it can legitimately exceed the liked count alone but cannot exceed the sum of both successful source batches. A resumed same-UID/source v2 task may retain its persisted union until the user explicitly starts fresh; pre-v2 unversioned likes/both state and output are intentionally isolated rather than resumed. Label these count bases instead of implying a contradiction.
- User-source and single-song paths both use descending `comment_new` cursors and shared half-open shard math, but retain different state/report/source-discovery lifecycles. Source comment pages default to 1000 and accept 1..2000; pooled source pre-shards unfinished ranges at startup to fill the actual bounded Worker/transport capacity, then adaptively splits further when Workers become idle.
- The GUI defaults to continuous scanning (`requestBudget=0`, no stop-after-first); CLI `scan` retains its finite per-run default and resumes from JSON checkpoints. `403/429`, explicit truncation, partial source failure, and operator stop affect status/coverage exactly as documented in this memory.
- Pooled scheduling is page-granular; both source and parallel modes adaptively bisect unread ranges when Workers are waiting. Structured events distinguish ordinary failures, explicit rate limits, and scheduler splits.
- The dashboard shows one global progress bar: source counts completed songs and parallel uses cursor-weighted time coverage. A dedicated central activity table keeps scheduled-song rows stable across page/request gaps while showing instantaneous active Worker counts; it is presentation, not completion authority. Comment totals remain optional API data. The runtime timer freezes at the terminal elapsed value, while the live speed metric is the server's rolling count of comments actually returned by successful pages and returns to zero at task end.
- There is no database. Results are de-duplicated JSONL and durable state is atomic JSON. CLI/web defaults use repository-local `.ncm/` and `data/`; packaged Electron uses its `userData` directory. Target-v3 gives each source an isolated per-UID checkpoint while sharing only the canonical per-UID result and complete-song ledger; legacy/v2 files remain on disk but are never auto-imported into trusted v3 storage.
- Cross-version GUI recovery uses both `data/resume-task.json` (form parameters only) and the mode-specific scan checkpoint (progress). Restore does not auto-start and must leave `fresh` disabled. Windows installation stops the active scan, waits for terminal status/final checkpoint, and aborts on timeout before calling the updater.
- An old offset checkpoint is migrated by rescanning only unfinished/truncated songs from its immutable creation-time cursor. Changing cursor page size requires a fresh state, while existing JSONL still de-duplicates IDs.
- A lane is a verified proxy endpoint/egress; per-IP permits are capped by `workersPerLane` and all requests on a lane share one Governor. Dashboard Worker loops are hard-capped by `hostConcurrency` and acquire every page's lane from one fair allocator spanning all selected healthy exits. Proxy-backed lanes also share an adaptive task gate at the same configured ceiling: clustered transient failures lower effective transport concurrency and increase aggregate start spacing, then stable success restores transport capacity gradually without changing the Worker-loop count. Recovering lanes temporarily stop receiving permits and wake allocator waiters at their deadline; unavailable exits shift capacity to healthy lanes. If all lanes look unavailable while an in-flight request may still restore one, allocator waiters remain alive until that request settles; only proven exhaustion ends the Worker loops and pauses the invocation. This never deletes a lane from the managed pool. Managed/external pools are verified against both public egress IP and NetEase, isolated by IPv4 `/24` or IPv6 `/48`, configurable from the dashboard (current defaults 8 exits from 48 candidates), and rechecked in non-overlapping background rounds. `maxProxyLanes=0` uses all ordered verified exits; a positive value caps the task subset without changing pool capacity.
- Liked-song IDs and old unnamed source checkpoints are hydrated through best-effort batched backend song-detail calls (maximum 500 IDs per batch). Candidate order and successful earlier batches are preserved/checkpointed even if a later metadata batch fails. Pooled batches rotate across healthy metadata lanes and locally skip a lane after its optional `403/429`, without latching or blocking that lane for required comments. Current/result displays never launch per-row lookup requests. Live results are job-scoped and never re-sorted by the comment's historical publish time.
- Proxy credentials, cookies, QR data, state, and results are local sensitive runtime data and never release assets. The application is a loopback-local dashboard; routine tests do not exercise high-volume real traffic.
- Forecast speed is an estimate based on page size, configured concurrency/spacing, lanes, and latency; it does not predict AIMD. “当前读取速度” is instead a rolling measurement of comments returned by successful pages. Neither is a completion guarantee, and cooldowns, discovery, retries, or empty pages can make either differ from long-run throughput.
- Windows packaged clients support in-app updates only from updater-capable versions onward and a valid Release needs `.exe`, `.exe.blockmap`, and `latest.yml`. Web/macOS use the manual-release path; public macOS distribution still needs proper Developer ID signing/notarization beyond the local ad-hoc build.
- Source requires Node.js 20+ and keeps `@neteasecloudmusicapienhanced/api` pinned. The documented check/test/build commands and Windows package-validation workflow are release gates.
- Concrete version numbers, filenames, tags, download links, and "latest release" statements must match `package.json` and live GitHub state at publication time; prefer version-neutral instructions in long-lived prose.

## Common traps

- Editing only the estimator/UI can make a concurrency number look changed while execution still uses an old/default worker count. Trace and test the full topology path.
- Changing the managed pool's build size is not the same as choosing a smaller lane subset for one scan. Do not rebuild or destructively shrink the shared pool merely to honor `maxProxyLanes`; `0` means automatic use of all verified exits, while only a positive value caps one task's subset.
- A host Worker cap must not be implemented by slicing the lane array or static lane-bound groups. Build only the bounded number of Worker loops and let every page acquire from the shared allocator; permit accounting, not resident Worker ownership, enforces `workersPerLane` while all selected healthy exits remain reachable.
- The target-owned liked-playlist returns IDs without song titles. Do not render those IDs as if they were names, and do not fix the display with repeated renderer-side `/api/song` calls; hydrate/cache metadata in the backend and preserve the ID fallback when title lookup genuinely fails. Catalog completeness is not best-effort metadata: never treat `null` count as zero, prefer a conflicting detail count, accept an implicit empty list, checkpoint missing/malformed/truncated `trackIds`, fall back to `tracks`, or collapse the two required governed requests into a hidden nested call. Never reintroduce `likelist` for another user's catalog: Cookie-bound identity can silently select the wrong owner.
- Best-effort metadata isolation is deliberately narrow. Letting required comment/source calls use `executeBestEffort` would hide real rate limits; letting optional metadata use ordinary `execute` would let a title lookup's `403/429` cancel otherwise valid comment coverage.
- The metadata session's `cooldownLanes` is disposable enrichment state, not scan health. Sharing it with the pooled scanner's `blockedLanes` would incorrectly turn a failed title lookup into lost comment coverage; omitting it would repeatedly hit a known-cooled metadata lane on every 500-ID batch.
- Source scan and `scan-song` both use `comment_new` time cursors, but they retain different scheduling, state, defaults, and privacy/login behavior. `comment_music` is legacy compatibility only: endpoint evidence showed `limit=100` returned 100 records while 200/500/1000 returned only 20, which is why old offset pagination must not be extended for large pages.
- Multiple rotating Workers may visit one lane but still share that lane's Governor. Giving every Worker its own Governor would accidentally multiply the per-IP start rate.
- The hard Worker count, per-IP Governors, and task-wide proxy gate protect different boundaries. Do not remove any of them, place the gate outside Governor delay/backoff, or present the static Worker count/`hostConcurrency` as guaranteed live transport capacity: AIMD may temporarily lower `proxyTransportEffectiveConcurrent` and increase start spacing without deleting Workers.
- A normal network failure is recoverable lane work, not permanent pool removal. Requeue unfinished work exactly once and mark the invocation-local lane unavailable at five consecutive final failures, but wait for its other active requests before stopping the task: `LaneAllocator.mayBecomeAvailable` must keep idle Workers waiting while any in-flight request can still revive a lane. A late success clears recovery/unavailability and notifies waiters; final settlement without restoration lets proven exhaustion return `undefined`. Recheck cooldown/unavailable state and `recovery.ready` after `queue.take()` so a lane that entered backoff after permit acquisition cannot start new remote work. Use the scanner's single queue-closure listener to cancel recovery waits; do not attach repeated `Promise.race` reactions in the Worker loop.
- Pool entry count is not proof of independent capacity; only verified distinct egress IPs count as lanes.
- Source `both` may finish with partial coverage when one source is restricted. Keep `sourceErrors` and coverage semantics visible.
- A finished modern source checkpoint still refreshes and reconciles the selected catalog before returning; with no new IDs it must make zero comment-page requests, while new IDs clear `finished`/`coverageComplete` and become pending. When testing a changed incompatible configuration, use a fresh temp state path; do not silently mutate compatibility fields in old state.
- The resume descriptor only restores UI parameters; the checkpoint remains authoritative. Do not mark a restored task `fresh`, auto-start it, store secrets in the descriptor, or silently coerce an incompatible checkpoint.
- Dynamic parallel splits make `state.shards.length` larger than the configured `shardCount`. Status/settlement must report the actual array, while compatibility still compares the original configured count.
- The global progress bar and `activeSongs` list are presentation, not completion authority. Concurrent activity can change on every request, API comment totals can change, and parallel shard counts grow after a split; preserve checkpoint completion, monotonic total reconciliation, and time-coverage math rather than forcing UI state into durable scan semantics.
- Request `start` replaces that Worker's retained scheduled song and marks it active; `success`/`failure` only marks the matching retained entry inactive and clears its requesting page. Do not delete the row at a request boundary: source song removal requires emitted `done`/truncated progress, and parallel removal requires task terminal. The renderer must preserve keyed row nodes and mutate their cells instead of rebuilding the table.
- A shard-local `requestingPage` may remain 1 while other shards for the same song successfully advance. The renderer leads with `已读 ... · 已完成 {pagesProcessed} 页` (plus parallel `时间覆盖 ...%`) and appends `{workers} 个分片请求中 · 最长 ...` while work is in flight; only before the first success may it use the requesting-page/first-batch diagnostic. Never present the minimum request page or longest request age as aggregate completion, and do not discard a source progress row merely because it currently has zero Workers.
- Candidate-count labels require provenance. `/api/user` exposes separate current record/target-owned-likes probes; `catalogSongs` is the newest trustworthy upstream total, while task `songs` may also retain removed historical entries to protect progress. In `both`, compare with the ID union—not likes alone. A UID/source/catalog-version mismatch must fail compatibility; dashboard pre-v3 state/result/coverage paths remain unreachable rather than silently reusing old or wrong-owner data.
- Concurrent dashboard refresh triggers are normal. Keep the single-flight guard before the combined fetch so they share one request rather than creating stale responses or extra server load.
- Do not reintroduce interval-driven overlapping fetches, per-match whole-table rendering, decorative perpetual pool-row rotation, or full managed-process identity checks in `/api/pool`; these previously caused visible Electron stutter, especially from repeated PowerShell startup on Windows.
- A logger callback is observability only. Never branch scan correctness on successful logging, and never expose a caller-supplied log path through the HTTP API.
- Runtime paths differ: source/CLI defaults use the project root; packaged Electron uses `userData`. Never hardcode repository runtime paths in desktop code.
- `dist/` is generated from `src/` and ignored. Edit TypeScript sources, not compiled JavaScript.
- GitHub's generic latest-release check and native Windows `electron-updater` are separate paths. Test both when changing update UX. In particular, verify HTML release notes become plain text in the native updater state, not merely in a browser-only view.
- A source page-size control in the UI or estimate is not evidence that source scanning safely uses it. Trace the setting through CLI/UI, server, scanner, `comment_new` cursor update, state compatibility, and the legacy-checkpoint `createdAt` rescan path.

## Workspace GUI direction

The dashboard has one shared desktop shell but two deliberately separate platform workspaces. Global topbar tabs select NetEase or QQ; they are not scan modes. NetEase owns the fixed `parallel/source` mode group and QQ owns `song/likes`. Each platform remembers its own selected mode and output tab, while the durable renderer keys remain exactly `netease:parallel`, `netease:source`, `qq:song`, and `qq:likes`. The outer shell geometry is platform-neutral: both platforms use the same compact icon-only desktop rail, navigation item geometry and task-drawer anchor. Platform themes may change accent and workbench density, but must not expand the rail, reveal persistent navigation labels or move the main content track.

- The global platform tabs are an accessible roving tablist with `aria-controls`, `aria-selected`, one `tabindex=0`, and Left/Right/Home/End activation. The active workbench is visible; the other is both `hidden` and `inert`. Platform-only forms, identity, navigation labels, login action, colors, result/log presentation, SSE, remembered mode and output tab switch together. Leaving a platform cancels its song lookup; leaving NetEase `parallel` or QQ `song` for the sibling mode also cancels that lookup, but neither path cancels a formal scan. Cancelling a QQ lookup does not eagerly remove its controller from the global busy set: task start remains blocked until the aborted async request settles and its `finally` releases that controller.
- Platform presentation is separate from task identity. `TASK_VIEWS`, generations, latest jobs, settlements, estimates, results, logs and SSE remain keyed by the complete four-view key. Platform switches increment both platform and mode versions; mode animation commits only while its owner platform and version still match, and task-start responses render only into the originally requested view. A mode switch immediately renders the target view's cached/empty snapshot before its slide completes. If a completed platform transition reports `committed=false` or leaves the wrong platform active, the application layer synchronously applies the requested platform, presentation, snapshot and SSE before refreshing. Re-selecting the current platform performs the same convergence refresh. A QQ generation still invalidates only its stale QQ sibling where the single QQ Manager requires it.
- Platform changes use `web/platform-wave.js`: one 760 ms WebGL2 crest travels diagonally from lower-left to upper-right and commits the new workspace at 46% progress. The main content layer rises and gently tilts with the crest, then returns exactly to rest. Rapid switches cancel the old transition; completion, cancellation and `pagehide` remove the canvas and inline `transform`/`will-change`.
- The wave is bounded decoration: one fixed pointer-transparent canvas using the `low-power` WebGL preference, antialias/depth disabled, 72 crest segments, at most 68 particles on desktop or 36 at `<=820px`, DPR `1..1.25`, and one finite RAF loop. Context acquisition, shader/program/buffer setup, DOM setup, draw, commit and cleanup are exception-safe; partial GPU objects are released, initialization failure and normal teardown explicitly request `WEBGL_lose_context`, teardown operations are best-effort, and the transition promise always settles even after context loss or a throwing commit. Cancelling before commit preserves the source platform; cancelling after commit preserves the committed target while both paths release GPU state. Do not capture DOM textures, animate dense live lists or make it perpetual.
- `prefers-reduced-motion`, a hidden document, missing/throwing WebGL2 context, initialization/draw failure, a newly enabled reduced-motion preference, visibility loss or context loss uses the immediate/settled path. Final focus, roving tabs, live region, `hidden`/`inert` and ARIA state must match the animated path. While animation is active, the body is `aria-busy` and task-start surfaces reject clicks.
- The desktop topbar remains sticky. The task drawer is fixed and initially closed; Search, Settings and Pool remain toggles, and opening a central output closes the drawer. Navigation labels stay visually hidden on the desktop rail and are exposed through accessible names/tooltips. The task drawer opens from the shared rail edge for both platforms. The top task bar still owns target/mode, `hostConcurrency` (1..32), task exit upper bound (`0` = all verified exits), topology and start/stop. The center retains total progress, six metrics and accessible output tabs; speed/activity/result presentation never determines durable completion.
- Output tabs retain roving keyboard activation and `tabSwitchVersion` convergence. Results/log request generations suppress stale data; accepted snapshots merge behind newer SSE rows. Pool source animations, task-start responses and pool mutations keep their own version ownership. Clash selection, running-pool initialization and accessible pool status behavior remain unchanged.
- The proxy inspector remains a sticky desktop column that collapses to 54 px; at `<=1280px` it becomes a fixed overlay with a 48 px visible toggle edge. The overlay inspector and task drawer are mutually exclusive so resizing cannot stack them over each other. Collapse moves focus before applying `inert`/`aria-hidden`, and reduced motion removes transitions without changing state. The main-pane container boundary remains `<=1210px`, task actions and toolbar fields shrink/wrap at `<=560px`, and at `<=820px` the rail becomes a six-item top row. Horizontal or vertical resizing must not make the topbar, platform tabs, window controls, rail, command bar, drawer or inspector collide or create document-level horizontal overflow; tables, tabs and long panels scroll inside their own bounded containers. The EncryptUin dialog fits short screens with `max-height: calc(100dvh - 24px)` and internal content scrolling. On Windows widths `821..1000px` (including 900 px), brand/status/action labels collapse while the platform tabs and window controls remain usable; the hidden login text retains the stable accessible name `aria-label="二维码登录"`.
