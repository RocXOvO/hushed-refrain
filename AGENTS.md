## Product and runtime shapes

The application locates public comments authored by a target user on NetEase Cloud Music or QQ Music.

- NetEase matches a numeric UID exactly. The UID guide sends users through the NetEase web profile in a browser and reads the consecutive digits after `id=` in the address bar; it does not direct them to client sharing.
- QQ resolves a numeric QQ, official profile URL, or opaque EncryptUin to a canonical EncryptUin and matches the complete opaque author value.
- Runtime shapes are the NetEase CLI (`src/cli.ts`), QQ CLI (`src/qq-cli.ts`), loopback web dashboard (`src/server.ts`), and Electron desktop (`src/electron-main.ts`).
- Keep the dashboard on `127.0.0.1`. The server does not yet enforce a complete remote-mode Host/Origin/CSRF boundary.
- Packaged runtime data is under stable Electron `userData`; source CLI/web defaults use repository-local `.ncm/` and `data/`.
- There is no database. Checkpoints are JSON and results/logs are JSONL. Generated/runtime `dist/`, `release/`, `.ncm/`, `data/`, and `tmp/` are ignored and must not be committed.
- The dashboard has four independent view keys: `netease:parallel`, `netease:source`, `qq:song`, and `qq:likes`. Jobs, generations, results, SSE, logs, estimates, settlements, selected mode, and output tabs must remain keyed by the complete view.

## Scan engines and ownership

The three engines share infrastructure, not pagination or state semantics.

### NetEase user-source scan

Entry points: `scan`, `/api/job`, `runPooledCommentFinder`.

- `source` is `record | likes | playlists | both | all`: `both` remains rank + liked songs, while `all` adds the target UID's owned public non-liked playlists. `recordScope` is `all | week | both`; dual scope retains distinct `record` and `record-week` evidence.
- Never use `likelist` for another user. Page `user_playlist(uid)`, accept a playlist only when `creator.userId` explicitly equals the target UID, split owned `specialType=5` into likes, and ignore subscriptions or entries with absent/mismatched owner evidence. Revalidate the owner on every `playlist_detail`; a requested UID is never an evidence-free alias for a playlist creator.
- Liked and ordinary playlist catalogs require an explicit `trackIds` array of valid, unique positive-decimal IDs; missing vectors, invalid/duplicate IDs, owner mismatch, duplicate/nonadvancing list pages, or `more=true` with no entries remain hard source errors. A declared positive count with an empty vector is also invalid. Present list/detail `trackCount` values must be non-negative integers; null/empty is unknown, not zero.
- The target liked playlist has one deliberate partial-access rule: when its explicit vector is non-empty, valid, and unique but shorter than the largest list/detail declaration, scan that accessible subset immediately, emit a `sourceNotice` with the missing count, and keep `coverageComplete=false`. `PartialSongCatalogError` carries this deterministic subset through Governor/scanner control flow without retrying the same response, rotating to another Lane, or reducing adaptive transport capacity. Ordinary user playlists retain strict count completeness, and a liked vector that exceeds a declaration by more than the accepted one-song snapshot lag still fails.
- Merge all successful selected catalogs by song ID and scan one copy. Preserve the union in `sources[]` and per-source rank/play-count/score evidence in `memberships[]`; legacy state without memberships is synthesized during reconciliation. A failed record scope or playlist detail may retain other successful sources plus a source error, but an independently selected source that wholly fails must fail the scan.
- A privacy-restricted listening rank or liked playlist is a source notice, not a task/source error: skip only that source, continue every available selected source, and keep coverage incomplete. If it is the sole selected source, finish with a confirmed zero-song catalog plus the friendly notice rather than a raw 422 task failure. Actual transport, protocol, owner, or catalog-integrity failures remain source errors. Legacy persisted 422 strings must also render as the same friendly notice.
- For `recordScope=both`, a successful all-time ranking is the complete song catalog; an absent/private weekly ranking contributes no extra songs and is optional metadata rather than a task error. A literal `weekData:[]` is a valid zero-song weekly result. If the whole catalog refresh fails but a prior complete catalog exists, continue from that checkpoint and present a neutral retained-catalog notice while preserving the detailed diagnostic in state/log data.
- NetEase `CommentScope` is `root-only-v1 | root-and-floor-v1`; both dashboard scan views default to `root-only-v1`. Enabling floor replies must show the persistent warning that it can reduce scan speed dramatically. Root-only performs zero floor discovery/request I/O and uses separate `-root-only` state, result, and coverage paths. Scope is an immutable compatibility key: completion, coverage, checkpoints, and results are never reused across scopes; restored tasks keep their saved scope, and legacy descriptors keep their compatibility migration to full scope.
- `comment_new` returns top-level comments only, even though its `totalCount` includes top-level comments plus floor replies. Page it with a strictly descending time cursor, default page size 1000, accepted range 1..2000; a `hasMore` page must advance and an empty advancing page is valid. A root's normalized `replyCount` is only a floor-discovery hint, never completion authority.
- In `root-and-floor-v1`, each discovered `(songId,parentCommentId)` is independent durable, page-granular work. Page `comment_floor` in batches of 40 from `time=-1`; while `hasMore=true`, its time cursor must strictly increase, and only `hasMore=false` completes it. The same parent is strictly single-flight, so one huge parent is protocol-bound to roughly `40 / (RTT + local overhead)` replies/second and may remain near 40/s even with many exits. Different parents and songs may use multiple Lanes; a successful next page may rotate Lane, and failed ownership may transfer without spending a second logical budget slot. Persisted unfinished floors are prioritized on resume without serializing unrelated parents. Each page's matching rows are persisted as one `appendBatch` write + fsync before its cursor, counters, and checkpoint advance.
- Only the unsharded newest-page chain may start with `pageNo=1`. Every newly created, resumed-capacity, or adaptively split explicit-cursor time shard starts a fresh non-first-page chain at `pageNo=2`; never inherit `1` or an unrelated predecessor page number.
- Work is page-granular and fairly requeued. Pooled scans pre-shard unfinished song ranges to available Worker/transport capacity, then adaptively split unread half-open ranges when Workers wait.
- Full-scope per-song completion requires durable half-open root-time coverage plus every persisted floor at `hasMore=false`; root-only completion requires root coverage alone. Each song persists its immutable `commentEndTime`; trusted release metadata may set `coverageStartTime` for root accounting while the Scanner still reaches the global 2000 safety bound. Full scope presents searched top-level comments plus replies over the upstream combined total and lists the page types separately. Root-only explicitly says that upstream total includes unread replies, never uses it as a top-level percentage denominator, and PDF output says floors were not read. Totals are display hints, never terminal authority.
- `pageInSong` and `maxCommentPagesPerSong` count only top-level `comment_new` pages across a song's cursor and shards. In-flight root permits count toward that cap and failed requests release their permit; floor pages are not truncated by this setting and continue under the logical request budget. Reaching the top-level cap with unread root coverage is the distinct `truncated` terminal state `达到页数上限`; natural root completion on the last permitted page still wins, but the song is not complete until all discovered floors finish.
- A normal start refreshes and reconciles the selected catalog by song ID. Preserve prior cursor/shard progress, retain removed historical entries, and scan only genuinely new IDs. `--fresh` bypasses checkpoint/coverage reuse but does not clear canonical results.

### NetEase single-song parallel scan

Entry points: `scan-song`, `/api/parallel/job`, `runParallelSongScan`.

- Split `[startTime,endTime)` into non-overlapping half-open root-time shards and paginate each with descending `comment_new` cursors, without a login cookie. Under full scope, persisted floors retain independent ascending cursors, are prioritized before resumed root work, and may run concurrently across parents/Lanes; all root shards and floors must finish. Under root-only scope, no floor work exists and root shard coverage alone completes the scan.
- Fresh physical shard count is bounded by configured `shardCount`, actual Worker loops, and current transport capacity. The configured count remains the compatibility key; persisted/adaptive physical shard arrays are authoritative on resume.
- Adaptive splitting bisects only unread ranges and must never duplicate or skip coverage. Filter returned comments to the shard interval; JSONL de-duplication is a final idempotency guard, not a substitute for correct range math.
- Scheduler progress remains cursor-weighted root-time coverage rather than `completedShards / shards` or a comment-density estimate. User-visible comment progress is the combined top-level-plus-reply count over the upstream combined total, with root and floor page counts separate.

### QQ SeqNo scan

Entry points: `/api/qq/job`, `runQQMusicScan`; modes are `song` and `likes`.

- QQ state, results, pagination, transport gate, and writer are independent of NetEase time cursors and target-v3 storage.
- Song IDs and SeqNo values stay decimal strings; never convert them through JavaScript `Number`. The requested song ID remains the task primary key even when metadata supplies a MID or another response ID.
- Comment pages are 1..25 (default 25); public-liked discovery pages are 1..500 (default 500).
- The raw final normalized row is the next SeqNo cursor. Equal/local disorder inside a page is retained, but every resumed-page row must be older than the requested cursor. An unsafe page leaves that song unadvanced while other liked songs may continue.
- `song` always has one in-flight SeqNo chain. `likes` parallelizes different songs only.
- QQ results de-duplicate by `(songId,commentId)`. The writer completes `write + fsync` before match publication and state ownership; cancellation is checked again before cursor/checkpoint commit.
- One logical comment page is passed to `appendBatch`, which de-duplicates its composite keys and persists the page with one write and one fsync before publication. Both modes checkpoint after 400 ms or 4 dirty pages; likes Workers await every revision to keep the checkpoint-slot bound hard, while the serial song chain may replay at most four already-durable JSONL pages after a crash. Final, stop, cooldown, and failure paths force the outstanding flush.
- `QQJobManager` caches exact metadata returned by lookup/search (bounded to 32 entries). Song scans consume it only when its ID exactly equals `requestedSongId`; Scanner never performs an optional metadata request and never replaces the requested decimal-string primary key.
- Canonical identity and presentation are separate. Numeric and reversible classic QQ forms may display full `QQ <number>`; a reversible 28-character WeChat-login token displays only `微信用户`; accepted opaque targets display `EncryptUin <value>`. The user-visible default PDF filename deliberately includes the complete canonical UID/EncryptUin; logs, errors, diagnostics, fixtures, and release examples stay redacted/synthetic.

## Lookup and proxy boundary

- Ordinary dashboard lookups are low-frequency control traffic and always use a bounded local direct Lane: NetEase `/api/user`, `/api/user/profile`, `/api/song`, `/api/song/search`; QQ `/api/qq/user`, `/api/qq/song`, `/api/qq/song/search`, numeric canonical resolution, verification, and optional nickname/avatar enrichment.
- These routes ignore the running pool, manual-proxy fields, and forged proxy query inputs. QQ ordinary queries use a 4-second bound; NetEase UID preview overlaps profile, record, likes, and a shared first playlist page through one 100 ms Governor with two-second per-request bounds. Only confirmed liked-playlist privacy renders `已开启隐私`; an inconclusive ordinary preflight failure renders `暂时无法确认`, and cooldown remains separate.
- Opaque QQ canonical targets remain local. `微信用户` performs no profile enrichment and keeps fixed metadata/default avatar.
- Only formal high-volume comment/source pagination consumes the configured pool/static proxy. When a proxy path is selected it is fail-closed and never silently falls back to direct.
- Dashboard parallel requires a running verified pool. Source requires a verified pool, explicit static proxy, or explicit `allowDirect`. The shared pool proves egress and NetEase reachability, not QQ-domain reachability.
- UI button disabling is convenience only; server validation and `TaskCoordinator` leases are the in-process authority.

## Concurrency, rate control, and cancellation

- A Lane is one client/proxy endpoint plus one Lane-owned `RequestGovernor`. All requests using that exit share its literal `minDelayMs + jitter` start-slot schedule; Worker count never divides that interval.
- NetEase `workersPerLane` is a per-exit permit bound. Actual Worker loops are `min(lanes * workersPerLane, hostConcurrency)`; `hostConcurrency` is 1..32, default 8. Thirty-two Workers across eight verified exits requires `maxProxyLanes=8`, `workersPerProxy=4`, and `hostConcurrency=32`; setting only the exit and host caps is insufficient. The source form still defaults to one Worker per exit.
- QQ `song` has one Worker. QQ `likes` uses `hostConcurrency` Workers and derives `workersPerLane = ceil(hostConcurrency / selectedLanes)`.
- All page Workers acquire a Lane from one fair round-robin `LaneAllocator`; a host cap must not be implemented by slicing away selected exits.
- Proxy-backed tasks also share one task transport gate. Healthy aggregate starts are separated by at least 50 ms, a deterministic theoretical ceiling of 20 starts/second before per-Lane/network limits, not observed Internet throughput. For both NetEase and QQ, a request first acquires Gate capacity and its aggregate start slot, then reserves the selected Lane Governor at the actual HTTP-start boundary; retries use the same path. All four dashboard scan forms and new NetEase source/parallel CLI and server tasks default each Lane to 300 ms plus `U[0,100)` ms jitter, preserving aggregate starts at least 50 ms apart and same-exit starts at least 300 ms apart. Explicit saved values and historical resume fallback semantics remain authoritative for restored tasks. A local synthetic integration run with 32 independent parents, eight exits × four Workers, 200 ms synthetic RTT, full 40-reply pages, and those spacing controls observed about 713 replies/second on that machine; it is synthetic evidence, not a real-network promise. NetEase AIMD reduces effective transport capacity after clustered transient failures and gradually restores it without destroying Worker loops.
- Pool build/import/verify/refresh uses a separate 4-request/80-ms gate.
- Final ordinary Lane failures requeue unchanged work and enter cancellable exponential recovery. Five consecutive final failures mark that invocation's Lane unavailable; a late in-flight success may revive it. Do not declare exhaustion while a request can still restore a Lane.
- Each Manager owns an `AbortController`. Stop closes queues, aborts Governors/gates, cancels LaneRecovery and allocator/checkpoint waiters, prevents new remote starts, then forces the final checkpoint before releasing the lease.
- Request budgets count each logical NetEase history, top-level, or floor page once. Pooled source and parallel scans key an in-flight root page so cross-Lane failover reuses both its budget reservation and its top-level page-cap permit; physical retry/failover, catalog/source requests, and song metadata hydration do not consume another slot. The serial CLI Scanner applies the same logical-page budget to `user_comment_history`, `comment_new`, and `comment_floor`. GUI `0` means unlimited.

## State, persistence, generations, and presentation

- `src/atomic-file.ts` owns unique same-directory temporary files, fsync, bounded Windows rename retry, and newest-complete recovery. Once a JSON candidate parses, schema/decode failure is authoritative and must not fall back to older state.
- `JsonlResultWriter` owns one long-lived append handle opened with mode `0600`, loops until each complete batch is written, and `sync()`s before de-dup ownership, `onAppend`, cursor/count advancement, or checkpoint publication. Initialization preserves a malformed trailing fragment for diagnosis but durably inserts a newline before any future valid row; repair write/sync failure immediately closes that handle. Normal write/sync failure is latched for all later appends. `close()` rejects new appends but drains every append it already accepted before closing, and every serial, pooled, parallel, stop, failure, and cancellation exit awaits it. Pooled/parallel floor pages batch all matches into one write + fsync. Their forced checkpoint chain is single-flight: force after four completed pages or when a page completes at least 400 ms after the prior forced checkpoint; pages becoming dirty during an in-flight write remain dirty for the next forced batch. Terminal, stop, and error paths force again. JSONL may lead state, so recovery may replay an already durable page but de-dup must prevent duplicate results.
- NetEase source state and coverage are version 4; canonical result JSONL deliberately remains target-v3, and parallel state is version 2. Source state, coverage, and parallel compatibility all bind `commentScope`. Root-only uses separate `-root-only` target-v4 state/coverage and target-v3 result paths, so checkpoints, completion, coverage, and rows cannot cross scopes even though result-row `route` and parent fields require no schema bump. State owns per-song root cursors/shards, independent `(song,parent)` floor cursors/counts, source catalog version 3, cooldown, and truncation.
- Scoped record paths include non-default `recordScope`. The one legacy weekly checkpoint that occupied an all-time path is migrated under a shared file lock: accept only exact UID/source/week identity, atomically establish or preserve the matching scoped target, reread it for durable verification, then remove only the conflicting legacy document and its owned recovery files. Identity conflict leaves the legacy file intact and fails safely.
- Parallel state version 2 binds comment scope, immutable range/configured-shard/page-size identity, adaptive root shards, and any persistent floor cursors. Resume descriptor version 4 stores `includeCommentFloors`; older descriptors default to full scope. Scope mismatch fails compatibility rather than borrowing another scope's progress or output.
- QQ state is version 1, `kind:"qq-comment-scan"`, `commentPagination:"seqno-v1"`, in `data/qq/`. QQ and NetEase retain independent writers and de-dup domains, but both now preserve complete-write + fsync, damaged-tail isolation, latched persistence failure, publish-after-sync, and result-before-checkpoint ordering.
- `data/resume-task.json` is an atomically written private version-4 form descriptor with `requestIntervalSemantics:"per-start-v1"`. It never replaces checkpoint compatibility, stores no credentials, restores with `fresh=false`, and never auto-starts.
- Generation-bound REST/SSE/log/report reads must validate platform, mode, UUID, canonical target, and owned paths before and after asynchronous reads. UI snapshots/progress are presentation, never completion authority. NetEase source reports expose `catalogLoaded` from durable `sourcesLoaded`: `false` with zero means the catalog has not been read and its size is unknown; only `true` with zero is a confirmed empty catalog.
- NetEase source discovery publishes best-effort `onCatalogActivity` messages for rank, liked songs, owned playlists, and final scan preparation together with physical catalog requests started. `JobManager` exposes that stage in `note` and advances the visible request counter while `catalogLoaded=false`; the first comment-page request clears the stage. This presentation signal never changes request-budget accounting, catalog correctness, or checkpoint authority.
- The NetEase source selector owns one geometry-driven sliding highlight. Switching to `likes` or `playlists` collapses the record-scope region through a reversible CSS grid transition while semantic `aria-hidden`/`inert` state changes immediately; rapid reversal, resize, BFCache, platform switching, and reduced-motion must converge without queued animations or layout jumps.
- Responsive shell geometry is shared across both platforms. Above 1280 px, opening the fixed 336 px task panel gives `.main-pane` 367 px left padding so the sidebar right edge and content left edge stay 21 px apart; at 1280 px and below, task panel and Inspector remain mutually exclusive overlays. The centered topbar uses symmetric outer columns: from 1238–1480 px both sides are at least 310 px, or 340 px on Windows with `.topbar-end` fixed at 340 px; from 821–1237 px both sides are at least 71 px, or 220 px on Windows with the end slot fixed at 220 px; at 820 px and below the end slot is 75 px. `.status-badge` is non-shrinking and non-wrapping. The portal stays continuous at the 1210/1211 and 1280/1281 boundaries, and NetEase↔QQ switching keeps its x/width unchanged (`dx=0`, `dw=0`). Real QA covers Windows 150% at 1293×841 CSS px and browser 820/390 px without topbar or document overflow.
- The left rail contains only task configuration in its main list and global settings in its footer. Results, active songs, logs, exits, and estimates remain available through the main output tabs and Inspector rather than duplicate rail entries. At `<=820px`, task configuration and settings stay at opposite ends of the compact rail without stretching either control.
- The active-song table is active work, not task history: unfinished songs and truncated warning rows remain visible, while every normally completed song (including an accessible-range completion) is removed from the rendered rows and count immediately. Durable aggregate completion stays in task metrics/checkpoints.
- `web/pointer-silk-trail.js` is optional presentation only: `PointerSilkTrail.create({host,platform,enabled})` owns one lazy WebGL2 surface inside `#mainWorkspace`, accepts fine mouse input only, and exposes `setEnabled`, `setPlatform`, reason-based `suspend`/`resume`, and `destroy`. Four independent 20-point chains use deterministic spring/friction samples; increasing springs pair with decreasing friction to avoid high-spring/high-momentum resonance, each frame propagates points 19→1 from prior-frame predecessors before updating the head, and head lag has a 32 px soft cap. For 100 px circular input over 240 frames at 0.18, 0.20, 0.215, and 0.265 rad/frame, every point on all four lines must remain within a 160 px envelope. World-space width and offsets project into CSS pixels, capped at 22 px and 26 px respectively; material opacity is 0.76. One preallocated upload feeds four anti-aliased `TRIANGLE_STRIP` draws, with no textures, FBOs, randomness, blur, post-processing, or business-DOM capture. All RAF stops after the 72+348=420 ms idle tail; DPR stays at or below 1.25 and the color buffer at or below 800,000 pixels. Dialogs, platform transitions, hidden/blur/pagehide and reduced motion clear or release it; BFCache restore rebuilds it. Desktop settings v2 persist `cursorTrailEnabled` (default true), migrate v1 without losing `closeBehavior`, and accept partial updates; browser mode is session-only and never uses localStorage or a preferences API.
- Pointer-trail startup has a physical-movement gate. The first valid fine-mouse coordinate and mouse `pointerenter` establish only a baseline; setup or RAF scheduling requires a later client-coordinate change or nonzero movement delta. `wheel` and capture-phase `scroll` immediately clear/cancel the current tail; scrolling only marks geometry dirty and never reads layout, resizes the backing buffer, seeds a trail, or starts RAF. The next real `pointermove` refreshes geometry once before starting a fresh tail. `resume(reason)` only removes that suspension reason and never schedules or revives stale motion.
- Match/logger/UI callbacks are best effort. They must not alter scheduling, results, checkpoint advancement, coverage, or task terminal status.

## Proxy pool and desktop safety

- `src/mihomo-pool.ts` supports managed Clash Verge generations and external HTTP/HTTPS proxies. Only loopback listeners are generated; credentials and controller secrets remain private and masked from APIs/logs.
- Verification requires public egress plus a real NetEase comment probe. Select one fastest entry per IPv4 `/24` or IPv6 `/48`; only distinct verified egresses are scan Lanes.
- Managed replacement is new-before-old and descriptor-atomic. Killing/stopping a PID requires full executable plus exact generation-config identity. The frequent `/api/pool` status poll uses cheap liveness only and is not connectivity proof; task start re-verifies.
- Default pool sizing is 8 selected exits from 48 candidates. `maxProxyLanes=0` selects all verified exits for one task; a positive value caps only that task and never shrinks the shared pool.
- Pool `starting` and background `refreshing` share the same bottom-right status-capsule stack as task startup and transient notices. The stack vertically orders simultaneous surfaces, moves left of an expanded desktop/overlay Inspector, reserves the collapsed Inspector rail/peek area at every breakpoint, and hides on narrow screens while the full Inspector is open rather than covering it. A stable building/refreshing/hidden signature prevents repeated live-region writes or replayed arrival animation during polling; expanded Inspector keeps the redundant pool capsule hidden because its live state is already visible inside the panel.
- Electron keeps `contextIsolation:true`, `nodeIntegration:false`, `sandbox:true`, a narrow preload bridge, and a single-instance lock. Single-instance UX does not protect CLI/Web processes from sharing a logical scan root; that cross-process lease remains open audit work.
- Main-window close requests use the renderer-owned `closeAppDialog`, not a native OS message box. A validated main-window-only IPC decision returns `cancel`, `background`, or `exit`; stale/duplicate decisions are ignored. Remembering a choice updates only `closeBehavior`. Exit keeps the dialog visible with checkpoint-safe progress while the existing bounded graceful-quit path stops the active task and waits for the final checkpoint; an unavailable renderer cancels the close instead of guessing.
- Windows update installation first blocks new work, stops the real globally active task, waits up to 45 seconds for terminal status/final checkpoint, and installs only after QQ lookup/pool barriers settle. Timeout or stop/status failure cancels installation.
- Native Windows auto-update needs one matching `.exe`, `.exe.blockmap`, and `latest.yml`. Generic GitHub update checking and `electron-updater` are separate paths.
- Startup update checks and the following 30-minute polling loop are silent and single-flight. The loop runs only while the page is visible, stops on pagehide, and checks immediately after visibility/BFCache restoration when the interval elapsed. The top-right update trigger stays hidden until a higher version is confirmed, and background checks never open the update dialog; clicking the visible trigger opens the already-confirmed generic or native updater snapshot. A native download failure with known newer-version metadata keeps the trigger available for retry.
- Desktop PDF export reports a monotonic cumulative `elapsedMs` from the start of export, including save-dialog time; stage-to-stage deltas may be derived but are not stored as independent durations. The summary uses a two-row 12-column card grid: compact metrics lead, long coverage text owns half of the second row, and all values top-align instead of being pushed to the bottom by the tallest sibling. Result rows stay in one semantic table so Chromium paginates from measured row heights and repeats the table header; the redundant body footer is hidden in print so it cannot create an orphan blank page. Do not reintroduce estimated row-unit batches or forced per-batch page breaks. NetEase floor matches are labeled as replies and show their parent comment ID. Full-scope parallel `coverageLabel` says only `任务尚未完整完成` below 100% root-time coverage, says `楼中楼尚未完成` only when root time is 100% but overall completion is false, and declares completion only when both root and floor are complete; root-only reports explicitly say floors were not read. `resultReportFilename` uses the complete canonical target as intentional user-visible output, then `sanitizeWindowsPdfFilename` replaces Windows-forbidden/control characters, removes trailing dots/spaces, avoids reserved device stems, caps the stem at 180 characters, and fixes the extension to `.pdf`. Filename regressions must cover both platforms, exact target visibility, forbidden/control characters, trailing dots/spaces, reserved device names, length, and extension. Packaged smoke must traverse renderer `window.ncmDesktop` → preload → IPC → hidden Chromium load/fonts/print → atomic write and observe `save-dialog, load-report, fonts, print, write, saved`, then verify the selected path and `%PDF-` header.
